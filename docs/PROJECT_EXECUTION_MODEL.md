# 项目执行模型

## 目标

本仓库按“产品负责人提出目标/想法，实施方负责完整交付”的方式推进。

## 默认授权范围

除明确需要业务方拥有决定权的事项外，实施方默认负责：

- 产品需求拆解与优先级
- 信息架构与用户流程
- UI/UX 方案
- 技术选型
- API Contract
- 数据模型建议
- 前端与后端代码实现
- Mock / Fixture
- 测试策略与缺陷修复
- 微信小程序工程配置
- 部署方案
- 发布前检查清单
- 技术文档与迁移文档
- 现有仓库复用、抽取、重构或淘汰判断

## 必须升级给业务方的事项

仅在以下情况停止并请求决策：

1. 涉及正式产品名称、机构署名、政治/历史表述等业务责任主体无法由技术方判断的事项。
2. 涉及付费、商业化、法律承诺、版权授权或对外发布责任的事项。
3. 需要真实微信 AppID、服务器密钥、第三方平台账号等外部凭证才能继续的事项。
4. 存在多个方案且会产生不可逆业务后果，并且现有架构无法通过默认原则消解的事项。

## 默认决策原则

当存在多个可行技术方案时，优先选择：

`用户体验清晰 > 可维护性 > 与现有架构一致 > 开发速度 > 局部性能优化`

涉及平台架构时优先：

`统一领域模型 > 复用已有能力 > Contract 解耦 > 物理部署统一`

## 工作流

```text
想法 / 目标
  ↓
需求拆解
  ↓
风险与缺口检查
  ↓
形成方案
  ↓
说明关键取舍
  ↓
代码实现
  ↓
测试 / 验证
  ↓
修复
  ↓
提交 / PR
  ↓
里程碑汇报
```

## 质量原则

“能运行”不等于完成。完成必须同时满足：

- 产品流程闭环
- 页面信息架构正确
- API 边界清晰
- 关键状态完整
- 错误可恢复
- Mock 与真实 API 可替换
- 微信运行环境可验证
- 发布要求可执行

## 现有资产处理

`xiao-opera-miniapp` 属于 migration source，不默认复制全部代码；实际迁移以功能价值、质量和新 IA 是否一致为准。

`news-media-system` 是后端业务控制面的候选事实来源，不在本仓库复制后端业务逻辑。

`yimengjingshen` / `YimengSpirit-Multimodal` 属于 AI / research lineage，不在体验层复制训练运行时。
